# DevOps 研发交付 Harness 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 基于 PRD v1.0 建设一套面向单研发团队、深度集成 GitHub 的 DevOps 研发交付平台 MVP。

**架构：** 平台内建需求、任务、测试、发布、验收、度量等业务对象；GitHub 负责代码仓库、分支、提交、PR、代码评审、GitHub Actions 和部署状态。实施过程按 Adapt 的需求到上线闭环推进，每个任务都必须保留源头、评审、开发、测试、发布、验收和复盘痕迹。

**技术栈：** 待工程初始化任务确定。默认建议为可部署 Web 应用、关系型数据库、GitHub App 集成、GitHub Actions 作为 CI/CD 执行引擎。

**Spec：** `docs/superpowers/specs/2026-08-18-devops-delivery-harness-prd.md`

## 全局约束

1. 团队范围：MVP 阶段一个团队、一个项目、一个 GitHub 仓库。
2. 产品边界：平台管理交付闭环，GitHub 执行代码协作与自动化流水线。
3. GitHub 集成方式：GitHub App。
4. CI 引擎：MVP 仅支持 GitHub Actions。
5. 合并硬约束：GitHub Branch Protection 是实际阻断层；平台负责计算和展示交付门禁。
6. 每个开发任务必须能追溯到 PRD 条款和本实施计划任务编号。
7. 每个开发任务完成时必须留下需求源头、评审记录、代码记录、测试记录、验收记录和复盘记录。
8. 每个任务必须有独立可验证产出，不能以“后续补充”作为完成条件。

## Adapt 流程留痕规则

每个任务执行时必须按以下闭环推进：

```text
需求源头 -> 任务澄清 -> 技术评审 -> 开发实现 -> 自动化验证 -> 交付验收 -> 复盘记录
```

每个任务必须在 PR 或提交说明中保留以下追踪信息：

```text
Source: PRD-章节号
Plan Task: HARN-编号
Requirement: 需求编号
Review: 评审结论
Tests: 测试命令和结果
Acceptance: 验收结论
Retro: 复盘项或“无”
```

推荐提交信息格式：

```text
feat(HARN-001): 初始化工程骨架

Source: PRD 15
Plan Task: HARN-001
Requirement: 建立可部署 Web 应用工程
Review: 技术方案已确认
Tests: npm test / npm run build
Acceptance: 工程可启动，基础健康检查通过
Retro: 无
```

每个任务完成前必须满足：

1. 需求源头清楚：能指出来自 PRD 哪一节。
2. 评审记录清楚：说明方案是否通过，有无风险。
3. 代码证据清楚：提交、分支、PR 与任务编号关联。
4. 测试证据清楚：列出执行命令和结果。
5. 验收证据清楚：列出可观察的用户价值或接口行为。
6. 复盘记录清楚：记录遗留问题、改进项或明确“无”。

## 文件结构规划

由于当前仓库只有 README 和 PRD，工程结构由 HARN-001 初始化。建议目标结构如下：

```text
apps/web/                         # Web 前端应用
apps/api/                         # 后端 API 服务
packages/domain/                  # 需求、任务、发布、门禁等领域模型
packages/github-integration/      # GitHub App、Webhook、Actions、Deployment 集成
packages/shared/                  # 共享类型、工具函数、常量
docs/superpowers/specs/           # 产品需求与设计规格
docs/superpowers/plans/           # 实施计划
docs/trace/                       # 每个开发任务的留痕记录
```

如果 HARN-001 最终选择单体框架，例如 Next.js 全栈应用，也可以把上述边界映射为：

```text
src/app/                          # 页面和路由
src/modules/                      # 业务模块
src/domain/                       # 领域模型
src/integrations/github/          # GitHub 集成
src/shared/                       # 共享能力
docs/trace/                       # 留痕记录
```

无论采用哪种技术栈，模块边界必须保持：

1. 需求、任务、测试、发布、验收、度量是平台内建领域对象。
2. GitHub 相关逻辑必须隔离在 GitHub 集成模块中。
3. 门禁规则必须独立于页面展示，便于测试和复用。
4. 状态机必须独立于具体 UI，便于 API、Webhook 和页面共用。

## 执行顺序

建议严格按以下顺序执行：

```text
HARN-001
-> HARN-002
-> HARN-003
-> HARN-004
-> HARN-005
-> HARN-006
-> HARN-007
-> HARN-008
-> HARN-009
-> HARN-010
-> HARN-011
-> HARN-012
-> HARN-013
-> HARN-014
-> HARN-015
```

原因：

1. 先有工程和留痕机制，再开始功能开发。
2. 先有领域模型、状态机和门禁，再建设页面和集成。
3. 先完成需求、评审、任务闭环，再接 GitHub。
4. 先完成 GitHub 代码和 CI 链路，再接测试、发布、验收。
5. 最后建设度量、工作台、配置，并做端到端验收。
