# DevOps 研发交付 Harness 实施计划 v2.0

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 基于 PRD v2.0 建设一套面向单研发团队、深度集成 GitHub 的 DevOps 研发交付平台 MVP。

**架构：** 平台内建需求、任务、测试、发布、验收、度量等业务对象；GitHub 负责代码仓库、分支、提交、PR、代码评审、GitHub Actions 和部署状态。实施过程按需求到上线闭环推进，每个任务都必须保留源头、评审、开发、测试、发布、验收和复盘痕迹。

**技术栈：** 待工程初始化任务确定。默认建议为可部署 Web 应用、关系型数据库、GitHub App 集成、GitHub Actions 作为 CI/CD 执行引擎。

**Spec：** `docs/superpowers/specs/2026-08-20-devops-delivery-harness-prd-v2.md`

**版本说明：** 本计划基于 PRD v2.0，在 v1 实施计划（HARN-001~015）基础上增量迁移：
- 保留全部任务编号与执行顺序，避免历史留痕断链。
- PRD 引用按 PRD v2 第 20 章映射表更新。
- HARN-006/007/008/010/013/014/015 补充 v2 新增要求（对账机制、未关联队列、部署多源汇总、Branch Protection 检查清单、审计留痕、15 条验收标准）。

## 全局约束

1. 团队范围：MVP 阶段一个团队、一个项目、一个 GitHub 仓库（数据层绑定模型 1:N，MVP 仅暴露 1:1）。
2. 产品边界：平台管理交付闭环，GitHub 执行代码协作与自动化流水线。
3. GitHub 集成方式：GitHub App，最小权限申请。
4. CI 引擎：MVP 仅支持 GitHub Actions。
5. 合并硬约束：GitHub Branch Protection 是实际阻断层；平台负责计算和展示交付门禁（PRD R-5）。
6. 每个开发任务必须能追溯到 PRD 条款（PRD v2 章节号）和本实施计划任务编号。
7. 每个开发任务完成时必须留下需求源头、评审记录、代码记录、测试记录、验收记录和复盘记录。
8. 每个任务必须有独立可验证产出，不能以"后续补充"作为完成条件。
9. 核心不变量（PRD v2 第 4 章）与规则强度分级（第 5 章）是本计划所有任务的行为约束。
10. 关键技术风险按 PRD v2 第 13 章应对：R-1 幂等/对账、R-5 Branch Protection、R-6 部署多源汇总、R-10 安全、R-3 未关联队列。

## Adapt 流程留痕规则

每个任务执行时必须按以下闭环推进：

```text
需求源头 -> 任务澄清 -> 技术评审 -> 开发实现 -> 自动化验证 -> 交付验收 -> 复盘记录
```

每个任务必须在 PR 或提交说明中保留以下追踪信息：

```text
Source: PRD-章节号（v2 编号）
Plan Task: HARN-编号
Requirement: 需求编号
Review: 评审结论
Tests: 测试命令和结果
Acceptance: 验收结论
Retro: 复盘项或"无"
```

推荐提交信息格式：

```text
feat(HARN-001): 初始化工程骨架

Source: PRD 1、17、19
Plan Task: HARN-001
Requirement: 建立可部署 Web 应用工程
Review: 技术方案已确认
Tests: npm test / npm run build
Acceptance: 工程可启动，基础健康检查通过
Retro: 无
```

每个任务完成前必须满足：

1. 需求源头清楚：能指出来自 PRD v2 哪一节。
2. 评审记录清楚：说明方案是否通过，有无风险。
3. 代码证据清楚：提交、分支、PR 与任务编号关联。
4. 测试证据清楚：列出执行命令和结果。
5. 验收证据清楚：列出可观察的用户价值或接口行为。
6. 复盘记录清楚：记录遗留问题、改进项或明确"无"。

## 文件结构规划

由于当前仓库只有 README 和 PRD，工程结构由 HARN-001 初始化。建议目标结构如下：

```text
apps/web/                         # Web 前端应用
apps/api/                         # 后端 API 服务
packages/domain/                  # 需求、任务、发布、门禁等领域模型
packages/github-integration/      # GitHub App、Webhook、Actions、Deployment 集成
packages/shared/                  # 共享类型、工具函数、常量
docs/superpowers/specs/           # 产品需求与设计规格（PRD v2）
docs/superpowers/plans/           # 实施计划
docs/trace/                       # 每个开发任务的留痕记录
```

如果 HARN-001 最终选择单体框架，例如 Next.js 全栈应用，也可以把上述边界映射为：

```text
src/app/                          # 页面和路由
src/modules/                      # 业务模块
src/domain/                       # 领域模型
src/integrations/github/          # GitHub 集成
src/shared/                       # 共享能力
docs/trace/                       # 留痕记录
```

无论采用哪种技术栈，模块边界必须保持：

1. 需求、任务、测试、发布、验收、度量是平台内建领域对象。
2. GitHub 相关逻辑必须隔离在 GitHub 集成模块中。
3. 门禁规则必须独立于页面展示，便于测试和复用。
4. 状态机必须独立于具体 UI，便于 API、Webhook 和页面共用。
5. Webhook 事件处理与对账逻辑必须隔离在集成模块内，且满足幂等要求（I-7、R-1）。

## 分阶段执行机制

> 本计划按阶段分批推进。**每完成一个阶段，必须停下等待人工确认与提交，确认通过后才进入下一阶段开发。** 严禁跨阶段连续开发。

### 阶段划分

| 阶段 | 任务 | 阶段目标（全部达成才算完成） | 阶段出口检查（人工确认项） |
| --- | --- | --- | --- |
| 阶段 1 | HARN-001 | 工程骨架可运行，留痕模板就绪，基础 CI 通过 | 工程可启动；测试/构建命令通过；留痕模板存在 |
| 阶段 2 | HARN-002、HARN-003、HARN-004 | 领域模型、状态机、门禁基础、需求与评审闭环 | 非法流转被拒绝；门禁返回失败原因；需求/评审可完整走通 |
| 阶段 3 | HARN-005 | 迭代与任务闭环 | 已评审需求可进迭代；任务可拆分、可流转 |
| 阶段 4 | HARN-006、HARN-007 | GitHub 集成基础：绑定、Webhook、分支/提交/PR 追踪、未关联队列 | 签名校验生效；重复事件无副作用；分支命名合规；未关联对象进队列 |
| 阶段 5 | HARN-008 | CI 同步与对账、PR 门禁可视化 | 事件缺失可通过对账恢复；展示同步时间与过期标识；PR 门禁显示失败原因 |
| 阶段 6 | HARN-009、HARN-010 | 测试缺陷闭环、发布部署闭环 | 阻塞缺陷阻止发布；部署多源汇总可用；发布不会卡死；回滚留痕 |
| 阶段 7 | HARN-011、HARN-012 | 验收复盘闭环、度量中心 | 关闭门禁生效；指标从留痕计算；样本不足有提示 |
| 阶段 8 | HARN-013、HARN-014 | 团队工作台、权限与配置中心 | 工作台聚合正确；角色权限生效；审计与豁免留痕 |
| 阶段 9 | HARN-015 | MVP 端到端验收（PRD 16 的 15 条验收标准 + 6 条风险验收项） | 全部验收标准通过；示例需求展示完整追踪链路 |

### 阶段执行规则

1. **MUST 逐阶段执行**：一个阶段内的任务按 HARN 编号顺序完成；未确认前不进入下一阶段。
2. **阶段内任务可并行**：同一阶段内的任务之间若没有依赖（如阶段 4 的 HARN-006/007），可在本阶段内并行执行；跨阶段永不并行。
3. **人工确认**：每个阶段完成后输出阶段总结（完成项、测试证据、遗留问题、PRD 覆盖确认），等待人工确认并提交（commit 或 PR）。
4. **人工确认内容**：代码审查、测试结果、留痕记录、是否同意进入下一阶段。
5. **确认后继续**：人工确认通过后，从下一阶段的第一个任务开始。
6. **阶段内变更**：人工确认时提出的修改意见，在当前阶段内修复并重新确认；未获通过前不得携带问题进入下一阶段。
7. **禁止跨阶段补课**：任何阶段不允许以"下一阶段再补"为由跳过本阶段出口检查项（全局约束 8）。

### 阶段完成信号

每个阶段结束时，向人工确认方提交：

```text
阶段：阶段 N（HARN-xxx 至 HARN-yyy）
已完成任务：列表
测试证据：执行的测试命令与结果
留痕记录：docs/trace/HARN-xxx.md 是否完整
遗留问题：无或具体列表
PRD 覆盖：本阶段对应的 PRD v2 章节
请求确认：是否进入阶段 N+1
```
