## 1. 产品定位

DevOps 研发交付 Harness 是一套面向单研发团队的一体化研发交付平台。平台负责管理需求、任务、测试、发布、验收和度量等业务交付闭环；GitHub 负责代码仓库、分支、提交、Pull Request、代码评审、GitHub Actions 执行和部署状态回写。

核心定位：

```text
平台管理交付闭环，GitHub 执行代码协作与自动化流水线。
```

平台把以下过程转化为可治理、可追踪、可门禁、可度量的研发交付系统：

```text
需求 -> 澄清 -> 评审 -> 排期 -> 任务 -> 分支 -> 提交 -> Pull Request -> CI/测试 -> 发布 -> 部署 -> 验证 -> 验收 -> 复盘
```

## 2. 目标用户

第一版面向一个具备产品、研发、测试和发布职责的单研发团队。

| 角色 | 核心诉求 |
| --- | --- |
| 产品负责人 | 收集需求，定义业务价值和验收标准，跟踪需求上线和业务验收。 |
| 开发人员 | 领取任务，创建分支，提交代码，处理 PR 评审和 CI 失败。 |
| 测试人员 | 管理测试用例、测试计划、缺陷、回归状态和质量门禁。 |
| 团队负责人 | 跟踪迭代进度、交付风险、阻塞、PR 状态和发布准备情况。 |
| 发布负责人 | 创建发布单，组织审批，触发部署，验证发布结果，记录回滚。 |
| 业务验收人 | 确认生产结果，完成业务验收。 |
| 交付管理者 | 查看周期、吞吐、质量、部署稳定性和流程瓶颈。 |

## 3. 产品目标

1. 每个需求都能从创建追踪到生产验收。
2. 每个研发任务都能关联 GitHub 分支、提交、PR、检查结果和部署结果。
3. 通过门禁规则阻止未经评审、未经测试、未经审批的工作继续流转。
4. GitHub Actions 的执行结果能在平台内可见，并驱动流程判断。
5. 发布单能关联需求、制品、环境、部署记录、验证记录和回滚方案。
6. 团队能看到工作卡在哪里，并能度量研发交付表现。

## 4. 核心不变量

> 不变量是产品与系统不可违反的原则。违反任一不变量时，停止实施并升级给产品负责人（ESCALATE）。

### I-1 事实源单一

GitHub 是代码协作与执行的唯一事实来源（分支、提交、PR、评审、检查、部署）；平台是交付业务对象（需求、任务、测试、发布、验收、度量）的唯一事实来源。平台内的 GitHub 相关数据一律是投影。

- 为什么：双写必然冲突，冲突必然导致门禁误判。
- 违反后果：状态分歧、追踪链断裂、度量失真。

### I-2 可自动同步的不人工录入

提交、PR、CI 结果、部署状态必须来自 GitHub 事件或对账，禁止人工双系统录入。

- 为什么：人工双录是数据腐化的第一来源，也是流程负担的根源。
- 违反后果：数据不可信、采用阻力上升。

### I-3 门禁只判断不替代

平台计算并展示交付门禁；合并硬约束由 GitHub Branch Protection 执行。平台不直接修改 GitHub 状态。

- 为什么：平台不是 CI/CD 执行层，绕过 GitHub 会破坏审计链与安全边界。
- 违反后果：门禁被绕过、审计失效。

### I-4 每条交付链路必须锚定需求

任务、分支、PR、测试、发布必须可追溯到需求。自动匹配失败的必须进入"未关联队列"等待人工关联，禁止静默丢弃。

- 为什么：追踪链断裂意味着门禁和度量全部失真。
- 违反后果：需求无法证明交付，产品目标 1/2 失效。

### I-5 所有状态流转必须留痕

状态变化必须记录操作者、时间戳、原因。度量只从留痕数据计算，不允许手工填报指标。

- 为什么：度量口径依赖完整的时间戳；无留痕则无度量。
- 违反后果：度量失真、复盘无据。

### I-6 不可逆操作先确认

触发生产部署、标记回滚、关闭需求、删除数据均为不可逆操作，必须二次确认。

- 为什么：生产影响不可撤销，误操作代价高。
- 违反后果：不可恢复的生产事故。

### I-7 外部事件处理必须幂等

Webhook 重复、乱序、丢失都不得产生重复数据或错误状态。事件处理结果必须可重放。

- 为什么：GitHub 不保证 webhook 投递次数与顺序（R-1）。
- 违反后果：数据污染、门禁误判。

### I-8 流程即配置

状态机、门禁规则、分支命名规范来自配置中心，禁止硬编码在业务代码中。

- 为什么：MVP 后流程演进需要配置化变更而不是重构。
- 违反后果：流程改动成本高、风险大。

## 5. 规则强度分级

### 5.1 MUST（必须执行）

1. 状态流转必须记录操作者、时间戳、原因（I-5）。
2. Webhook 处理必须校验签名且幂等（I-7、R-10）。
3. 平台创建的分支必须符合命名规范 `<类型>/<需求编号>-<任务编号>-<简短标题>`。
4. 需求进入开发前必须通过 10.1 门禁。
5. 发布单进入部署前必须通过 10.3 门禁。
6. 所有 GitHub 外部对象必须保存外部 ID 与最后同步时间（I-1）。
7. 关键操作（创建分支、触发部署、回滚、门禁豁免、状态强改）必须写审计日志。
8. 自动匹配失败的提交/PR/运行记录必须进入未关联队列（I-4）。

### 5.2 FORBIDDEN（禁止）

1. 禁止绕过 Webhook 签名校验处理事件。
2. 禁止平台直接合并 PR、改写 GitHub 分支或仓库状态（I-3）。
3. 禁止人工把对象置入状态机之外的任意状态；只能走配置的流转或管理员豁免并留痕。
4. 禁止静默丢弃无法匹配的提交/PR/运行记录（I-4）。
5. 禁止在业务代码中硬编码状态机、门禁规则或分支命名（I-8）。
6. 禁止把 GitHub App 私钥、Webhook secret、Token 写入代码库或数据库（R-10）。

### 5.3 DEFAULT（默认选择）

1. 实现选择优先最小、局部、可验证。
2. 部署状态来源优先级：`deployment_status` 事件 > workflow run 状态 > 人工确认。
3. 编号匹配顺序：分支名 > PR 标题 > 提交信息 > 人工关联。
4. 数据库优先关系型模型。
5. 未配置部署触发时，允许人工记录部署结果，但必须标记来源为"人工记录"。
6. 对账频率：部署与 workflow run 每 15 分钟、活跃 PR 与检查每 30 分钟、活跃分支与提交每 1 小时。

### 5.4 ESCALATE（必须升级）

以下情况必须停止并请求人类决策：

1. 变更规模超过单次实施切片边界。
2. 需要改变系统边界、公共契约，或数据结构中不可逆的部分。
3. 涉及生产部署、回滚、数据删除等不可逆操作（除非已明确授权）。
4. 两个核心不变量发生冲突。
5. 门禁被频繁豁免（见 R-8 升级条件）。
6. 对账发现不可调和的状态分歧（见 R-4）。

## 6. MVP 范围与非目标

### 6.1 MVP 范围

一个团队、一个项目、一个 GitHub 仓库，覆盖从需求到上线的完整交付闭环，包括：

1. 团队工作台、需求中心、评审中心、迭代与任务中心。
2. GitHub 集成（仓库绑定、分支创建、提交/PR/CI/部署同步）。
3. 流水线中心与门禁可视化。
4. 测试中心与缺陷闭环。
5. 发布中心与部署闭环。
6. 验收与复盘闭环。
7. 度量中心、权限与配置中心。

### 6.2 非目标（MVP 不做）

1. 多团队项目组合管理。
2. 复杂版本火车治理。
3. 自研 Git 代码托管系统。
4. 自研 CI 引擎。
5. 企业预算、采购、供应商管理。
6. 大型组织复杂权限矩阵。
7. 跨团队高级测试资产平台。
8. 跨系统架构治理。
9. 全量 AI 自动生成需求或全自动交付。

```text
创建需求
-> 需求澄清
-> 业务评审
-> 技术评审
-> 进入迭代计划
-> 拆分研发任务
-> 创建 GitHub 分支
-> 开发提交代码
-> 创建 Pull Request

-> GitHub Actions 构建与测试
-> 质量门禁检查

-> 生产验证

-> 复盘与度量

```

```text
-> 提交
-> Pull Request

-> 构建制品
-> 发布单
-> 部署记录
-> 生产验证
-> 业务验收
-> 复盘项
```

## 8. 功能模块

### 8.1 团队工作台

团队工作台是团队日常入口，需要展示：

1. 我的未关闭需求。
2. 我的任务。
3. 等待我评审的 PR。
4. 失败或阻塞的 GitHub Actions 运行记录。
5. 等待审批或等待验证的发布单。
6. 等待验收的需求。
7. 当前迭代健康度。
8. 交付阻塞项和逾期事项。
9. 未关联队列待处理数量（见 11.4）。

### 8.2 需求中心

需求中心负责管理产品和业务输入。

必须支持：

1. 创建、编辑、归档和关闭需求。
2. 区分需求类型：业务需求、产品需求、技术需求、缺陷、合规需求、运维需求。
3. 记录需求来源、负责人、优先级、业务价值、预期收益、期望日期和验收标准。
4. 关联子任务、测试用例、缺陷、PR、发布单和验收记录。
5. 按配置的状态机流转需求，每次流转留痕（I-5）。
6. 展示需求在各阶段的停留时间和阻塞信息。

需求核心字段：

| 字段 | 说明 |
| --- | --- |
| ID | 稳定唯一需求编号，例如 REQ-001。 |
| 标题 | 简短、可读的需求名称。 |
| 类型 | 业务需求、产品需求、技术需求、缺陷、合规需求、运维需求。 |
| 来源 | 业务、产品、客户、事故、监管、研发等。 |
| 负责人 | 产品或需求 owner。 |
| 优先级 | P0、P1、P2、P3。 |
| 业务价值 | 为什么要做这个需求。 |
| 验收标准 | 需求完成的判断条件。 |
| 目标日期 | 期望日期，不等同于交付承诺。 |
| 状态 | 当前需求状态。 |
| 关联迭代 | 需求所属迭代。 |
| 关联发布 | 需求所属发布单。 |

### 8.3 评审中心

评审中心支持需求进入开发前的业务评审和技术评审。

业务评审检查项：

1. 业务价值是否清楚。
2. 用户或业务场景是否清楚。
3. 范围是否清楚。
4. 不做什么是否明确。
5. 验收标准是否可测试。

技术评审检查项：

1. 技术可行性是否确认。
2. 架构影响是否识别。
3. 依赖关系是否识别。
4. 技术风险是否记录。
5. 粗略工作量是否给出。
6. 测试和发布影响是否明确。

评审结论：

```text
通过
驳回
需补充
延期
```

### 8.4 迭代与计划

计划模块把已评审需求和团队交付容量连接起来。

必须支持：

1. 创建迭代，维护开始日期、结束日期、迭代目标和团队容量。
2. 将已通过评审的需求加入迭代。
3. 将需求拆分为研发任务。
4. 分配负责人和计划完成日期。
5. 展示计划工作、已完成工作、阻塞工作和结转工作。
6. 发现未评审需求被加入迭代时给出提醒或阻断。

### 8.5 任务中心

任务是研发执行的最小管理单元。

必须支持：

1. 在需求下创建开发、测试、文档、部署、调研等任务。
2. 维护负责人、估算、计划日期和状态。
3. 从任务创建 GitHub 分支。
4. 将提交和 PR 回写到任务。
5. 根据 GitHub 事件和人工操作推动任务状态流转，流转留痕（I-5）。

任务状态：

```text
待处理 -> 进行中 -> 待代码评审 -> 待构建 -> 待测试 -> 已完成
```

异常状态：

```text
阻塞
退回
取消
```

### 8.6 GitHub 集成

GitHub 集成负责连接平台内的交付对象和 GitHub 的代码协作、自动化能力。

必须支持：

1. 安装并配置 GitHub App。OAuth 可作为后续用户级便利能力，MVP 的集成授权以 GitHub App 为主（最小权限，R-10）。
2. MVP 阶段一个项目绑定一个 GitHub 仓库；绑定模型在数据层支持 1:N，MVP 仅暴露 1:1（R-11）。
3. 仓库绑定时执行 Branch Protection 检查清单并展示缺失项（R-5）。
4. 从任务创建 GitHub 分支，分支命名规范：

```text
<类型>/<需求编号>-<任务编号>-简短标题
```

示例：

```text
feature/REQ-001-TASK-003-login-rate-limit
```

5. 同步包含需求编号或任务编号的提交。
6. 同步 Pull Request 标题、状态、评审人、评审状态、标签、检查结果和合并状态。
7. 同步 GitHub Actions workflow run 和 check result。
8. 使用 GitHub Deployments 时同步部署状态。
9. 保存 GitHub 外部对象 ID 与最后同步时间，便于对账和重试（I-1）。
10. 保存原始事件 payload，支持事件重放（R-1）。

### 8.7 流水线中心

流水线中心展示 GitHub Actions 运行记录和质量门禁状态。

必须支持：

1. 展示分支或 PR 最新 workflow run。
2. 展示运行状态：排队中、运行中、成功、失败、取消。
3. 在可获取时展示失败 job 和 step 摘要。
4. 将流水线结果关联到 PR、任务、需求和发布单。
5. 在 GitHub 权限允许时支持重新运行。
6. 将构建和测试结果输入门禁判断。
7. 展示数据最后同步时间，超时显示过期标识（R-4）。

### 8.8 测试中心

测试不是开发后的孤立阶段，而是交付闭环的一部分。

必须支持：

1. 创建并维护关联需求的测试用例。
2. 为迭代或发布创建测试计划。
3. 记录手工测试执行结果。
4. 从 GitHub Actions 导入或同步自动化测试结果（I-2）。
5. 创建关联需求、任务、测试用例和 PR 的缺陷。
6. 标记缺陷是否为阻塞缺陷。
7. 存在阻塞缺陷时阻止发布准备完成（接入 10.3 发布门禁）。

测试结果状态：

```text
未执行
通过
失败
阻塞
跳过
```

缺陷状态：

```text
新建 -> 处理中 -> 已修复 -> 已验证 -> 已关闭
```

### 8.9 发布中心

发布中心负责生产变更的受控管理。

必须支持：

1. 创建发布单。
2. 选择本次发布包含的需求。
3. 关联 PR、制品、部署运行、测试计划和缺陷。
4. 记录发布环境、发布窗口、审批人和回滚方案。
5. 执行发布前门禁检查（10.3）。
6. 在已配置时触发 GitHub Actions 部署 workflow（workflow_dispatch）。
7. 同步部署状态（多源汇总：deployment_status > workflow run > 人工确认，见 5.3）。
8. 记录生产验证结果。
9. 在需要时记录回滚（不可逆操作，二次确认，I-6）。

发布单状态：

```text
草稿 -> 待审批 -> 待部署 -> 部署中 -> 待验证 -> 已发布 -> 已关闭
```

异常状态：

```text
已驳回
部署失败
已回滚
已取消
```

规则：发布单不允许自动跳转"已发布"，必须经过人工验证步骤（R-6）；部署超时显示异常状态并支持人工处理（R-6）。

### 8.10 验收与复盘

验收用于关闭上线后的业务闭环。

必须支持：

1. 记录生产验证结果。
2. 按验收标准记录业务验收结果。
3. 捕获未完成或验收失败项。
4. 将验收失败项转为缺陷或新需求。
5. 记录复盘项、负责人和跟进日期。

验收结果：

```text
通过
不通过
部分通过
需跟进
```

### 8.11 度量中心

度量中心帮助团队查看流动效率、质量和稳定性。

MVP 指标（口径在本 PRD 固定，实现不得自行变更，R-7）：

| 类别 | 指标 |
| --- | --- |
| 流动效率 | 需求总周期、阶段停留时间、等待时间。 |
| 开发效率 | 任务完成周期、PR 创建到合并周期、评审等待时间。 |
| 构建质量 | 构建成功率、失败运行次数、构建平均修复时间。 |
| 测试质量 | 测试通过率、阻塞缺陷数、重开缺陷数。 |
| 发布稳定性 | 部署频率、发布成功率、回滚率。 |
| 交付结果 | 需求吞吐量、准时率、验收通过率。 |

规则：

1. 指标全部从业务对象留痕数据计算，禁止手工填报（I-5）。
2. 样本不足时显示"样本不足"，不得显示 0 或空（R-7）。
3. 指标支持按迭代和日期范围筛选。

### 8.12 配置中心

必须支持：

3. 配置 GitHub 仓库绑定。
4. 配置默认分支命名规范（I-8）。
5. 配置用于构建、测试和部署的 GitHub Actions workflow。
6. 配置团队角色。
7. 查看门禁豁免记录与审计日志入口。

## 10. 门禁规则

> 每条门禁按"触发条件 → 判定 → 失败处理"组织。门禁失败时，必须展示失败原因与修复动作。

### 10.1 需求进入开发门禁

- 触发：需求尝试流转到"开发中"。
- 判定（全部满足才通过）：
  1. 业务价值已填写。
  2. 验收标准已填写。
  3. 业务评审已通过。
  4. 技术评审已通过。
  5. 需求已进入迭代计划。
- 失败处理：阻断流转，展示未通过项与修复动作；修复后重新判定。

### 10.2 Pull Request 合并门禁

- 触发：平台展示 PR 合并就绪状态（PR 或检查状态每次变化时重新计算）。
- 判定（全部满足才通过）：
  1. PR 已关联需求与任务。
  2. 至少 1 名评审人已通过。
  3. 必需的 GitHub Actions 检查已成功。
  4. 自动化测试已通过。
  5. 任务或需求下没有未关闭阻塞缺陷。
- 说明：平台负责计算并展示门禁结论与原因；实际合并阻断由 GitHub Branch Protection 执行（R-5 防漂移）。
- 失败处理：显示失败原因与对应修复动作。

### 10.3 发布门禁

- 触发：发布单申请执行"部署"动作。
- 判定（全部满足才通过）：
  1. 发布审批已完成。
  2. 发布包含的需求均已测试通过。
  3. 阻塞缺陷数量为 0。
  4. 已选择制品版本或 commit SHA。
  5. 已选择部署环境。
  6. 已填写回滚方案。
- 失败处理：阻断部署动作，展示失败原因。

### 10.4 需求关闭门禁

- 触发：需求申请流转到"已关闭"。
- 判定（全部满足才通过）：
  1. 生产验证已通过。
  2. 业务验收已通过，或已记录明确例外原因。
  3. 发布结果已记录。
  4. 需求相关度量已生成，或明确标记数据不足。
- 失败处理：阻断关闭，展示原因。

## 11. GitHub 集成契约

### 11.1 事件映射

MVP 需要处理以下 GitHub 事件：

| GitHub 事件 | 平台动作 |
| --- | --- |
| push | 当编号匹配时，将提交关联到分支、任务和需求。 |
| pull_request.opened | 在任务和需求下创建或更新 PR 关联。 |
| pull_request.synchronize | 刷新提交和检查状态。 |
| pull_request.closed | 标记 PR 已合并或已关闭，并在合适时更新任务状态。 |
| pull_request_review.submitted | 更新代码评审门禁。 |
| check_run.completed | 更新 CI 或检查结果。 |
| workflow_run.completed | 更新 workflow 结果和流水线视图。 |
| deployment_status | 更新部署记录和发布单。 |
| release.published | 可选关联 GitHub Release 到发布单。 |

事件处理规则：

1. MUST 校验 webhook 签名，未通过直接拒绝（R-10）。
2. MUST 幂等处理：按外部对象 ID + 事件类型去重，重复事件无副作用（I-7）。
3. MUST 保存原始事件 payload 与事件 ID，支持重放（R-1）。
4. MUST 处理失败进入重试队列，超过重试次数后人工可见（R-1）。

### 11.2 编号匹配规则

1. MUST 解析分支名中的需求编号和任务编号。
2. MUST 解析 PR 标题中的需求编号和任务编号。
3. DEFAULT 提交信息中的编号作为兜底匹配方式。
4. MUST 提供人工关联；自动匹配失败时对象进入未关联队列（11.4）。

### 11.3 对账机制（MUST，MVP 必建）

- 目的：弥补 webhook 丢失/乱序，收敛平台投影与 GitHub 事实（R-1、R-4）。
- 对象与周期（DEFAULT）：
  - 部署与 workflow run：每 15 分钟。
  - 活跃 PR 与检查：每 30 分钟。
  - 活跃分支与提交：每 1 小时。
- 对账只拉取最近 N 天活跃对象，控制 API 预算（R-2）。
- 对账结果写入最后同步时间；与事件流冲突时以 GitHub 当前状态为准，并在审计日志记录"对账修正"。

### 11.4 未关联队列（MUST）

- 无法通过自动规则匹配到需求/任务的对象（分支、提交、PR、workflow run）进入未关联队列。
- 队列在团队工作台可见，支持人工关联与标记"不关联"（标记需留痕）。
- 队列对象不允许静默消失（I-4）。
- 未关联对象超过 N 天未处理时告警（R-3）。

## 13. 关键风险与应对策略

> 每个风险按"触发条件 → 应对策略 → 验证方式 → 升级条件"组织。标注 MUST 的必须在 MVP 落实。

### R-1 Webhook 事件丢失、乱序、重复

| 维度 | 内容 |
| --- | --- |
| 风险 | GitHub 不保证 webhook 按序、恰好投递一次；网络故障、重投、乱序都会导致平台状态错乱 |
| 触发条件 | 事件重放、事件缺失、事件晚到；GitHub 侧投递失败后重试 |
| 影响 | 平台状态与 GitHub 分歧；门禁基于过期数据判断；重复数据污染 |
| 应对策略 | ① MUST 幂等处理：按外部对象 ID + 事件类型去重，重复事件无副作用；② MUST 保存原始事件 payload 与事件 ID，支持重放；③ MUST 建立 11.3 对账机制作为兜底；④ 事件处理失败进入重试队列，超过重试次数后人工可见 |
| 验证方式 | 注入重复、乱序、缺失事件的对账测试；重放测试后状态一致 |
| 升级条件 | 对账偏差持续无法收敛（如连续多个周期）→ ESCALATE |

### R-2 GitHub API 限流

| 维度 | 内容 |
| --- | --- |
| 风险 | 对账、同步、建分支等 REST 调用耗尽配额，同步停止 |
| 触发条件 | 仓库活跃度高、批量操作、配额预算未控制 |
| 影响 | 对账失败、事件处理积压、创建分支失败 |
| 应对策略 | ① MUST 读操作优先使用本地投影，事件已入库的数据不重复拉取；② 对账按 5.3 DEFAULT 频率并做请求预算；③ 命中限流时退避重试，暂停低优先级对账、保留事件处理；④ 配额状态可见 |
| 验证方式 | 限流注入测试：限流期间事件仍被处理，对账自动降频 |
| 升级条件 | 配额持续耗尽影响事件处理 → ESCALATE |

### R-3 编号匹配失败导致追踪链断裂

| 维度 | 内容 |
| --- | --- |
| 风险 | 分支/PR/提交无法解析到需求与任务，追踪链路断开 |
| 触发条件 | 分支命名不规范、直接在 GitHub 手工操作、PR 标题无编号 |
| 影响 | 需求无法证明交付；门禁、度量失真 |
| 应对策略 | ① MUST 平台创建的分支强制规范命名；② MUST 未关联队列承载无法匹配对象（11.4），工作台可见；③ MUST 提供人工关联能力；④ 关键对象未关联超过 N 天时告警 |
| 验证方式 | 孤儿对象处理测试；队列可见性测试 |
| 升级条件 | 未关联对象持续堆积超出团队处理量 → 升级流程负责人 |

### R-4 平台与 GitHub 状态分歧

| 维度 | 内容 |
| --- | --- |
| 风险 | 事件缺失或人工在 GitHub 直接操作（直接合并、强推）导致平台投影过期 |
| 触发条件 | webhook 未送达、GitHub 侧人工操作绕过平台 |
| 影响 | 门禁误判、度量失真、信任流失 |
| 应对策略 | ① MUST 对账机制（11.3）定期收敛；② MUST 所有投影展示"最后同步时间"，超过阈值显示过期标识；③ 对账冲突以 GitHub 为事实源并记录修正日志；④ 不可自动收敛的分歧进入人工裁决入口 |
| 验证方式 | 对账收敛测试；过期标识展示测试 |
| 升级条件 | 不可调和分歧 → ESCALATE |

### R-5 门禁双轨漂移（Branch Protection）

| 维度 | 内容 |
| --- | --- |
| 风险 | 平台展示门禁，但 GitHub Branch Protection 未配置或配置漂移，未评审/未测试代码实际被合并 |
| 触发条件 | 仓库绑定后未配置保护规则；保护规则被改动 |
| 影响 | 门禁形同虚设，交付质量承诺失效 |
| 应对策略 | ① MUST 仓库绑定时执行 Branch Protection 检查清单并展示缺失项；② 定期检测保护配置与平台门禁的一致性并告警；③ 门禁界面明确区分"平台建议"与"GitHub 强制" |
| 验证方式 | 绑定向导测试；配置漂移检测测试 |
| 升级条件 | 生产分支保护缺失且未修复 → ESCALATE |

### R-6 部署状态回写不可靠

| 维度 | 内容 |
| --- | --- |
| 风险 | deployment_status 事件缺失、workflow_dispatch 失败、部署在平台外执行，发布单卡死 |
| 触发条件 | 事件缺失、workflow 失败未上报、人工部署 |
| 影响 | 发布单长期停在"部署中"；发布状态不真实 |
| 应对策略 | ① MUST 多源汇总：deployment_status > workflow run > 人工确认（5.3）；② MUST 发布单不允许自动跳转"已发布"，必须经过人工验证步骤；③ 部署超时显示异常状态并支持人工标记；④ 人工记录必须标记来源 |
| 验证方式 | 事件缺失、超时场景测试 |
| 升级条件 | 生产部署超过设定时限无状态回写 → 通知发布负责人 |

### R-7 度量口径与数据完整性

| 维度 | 内容 |
| --- | --- |
| 风险 | 状态无时间戳、指标口径漂移、样本不足导致度量失真 |
| 触发条件 | 历史迁移、绕过留痕的状态改动、口径未固定 |
| 影响 | 基于失真的度量做错误决策 |
| 应对策略 | ① MUST 状态流转强制时间戳（I-5）；② MUST 指标口径在本 PRD 8.11 固定，实现不得自行变更；③ 样本不足时显示"样本不足"而非 0；④ 指标全部从业务对象留痕计算，禁止手工填报 |
| 验证方式 | 数据完整性检查；口径一致性测试 |
| 升级条件 | 口径争议 → 产品负责人裁决 |

### R-8 流程规避与紧急通道

| 维度 | 内容 |
| --- | --- |
| 风险 | 紧急修复、线下协作导致流程被绕过，平台沦为记录工具 |
| 触发条件 | 线上事故、特殊场景、流程负担过重 |
| 影响 | 门禁空转、数据不全 |
| 应对策略 | ① MUST 提供明确紧急通道：允许豁免门禁，但必须记录豁免原因与审批人，并在事后补齐流程；② 豁免全部进入审计日志；③ 门禁规则可配置（8.12）；④ 频繁豁免触发流程评审 |
| 验证方式 | 豁免留痕测试；豁免率报表 |
| 升级条件 | 豁免率超过阈值（如单迭代 > 20%）→ 流程本身需调整，升级团队负责人 |

### R-9 采用阻力与双重录入

| 维度 | 内容 |
| --- | --- |
| 风险 | 成员认为平台是额外负担，绕过或不全量使用 |
| 触发条件 | 操作繁琐、需要在 GitHub 与平台重复操作 |
| 影响 | 数据不全、追踪链断裂、产品失败 |
| 应对策略 | ① MUST 坚持 I-2：可自动同步的不人工录入；② 工作台为唯一日常入口，减少跳转；③ MVP 验收包含真实使用体验检查（第 16 章）；④ 能自动触发的状态流转尽量自动化 |
| 验证方式 | MVP 试用验收、操作路径检查 |
| 升级条件 | 使用率持续偏低 → 与团队访谈，调整流程与体验 |

### R-10 安全与权限误配

| 维度 | 内容 |
| --- | --- |
| 风险 | Webhook 伪造、密钥泄露、角色误配导致未授权操作 |
| 触发条件 | secret 管理不当、GitHub App 权限过宽、角色配置错误 |
| 影响 | 数据泄露、未授权部署、供应链风险 |
| 应对策略 | ① MUST Webhook 签名校验，未通过直接拒绝；② MUST GitHub App 按最小权限申请；③ MUST 密钥与 Token 只存在于环境变量/密钥管理，禁止入库和代码库；④ 关键操作审计日志；⑤ 角色变更留痕 |
| 验证方式 | 签名注入测试；审计日志测试 |
| 升级条件 | 任何疑似未授权操作 → 立即升级并暂停相关入口 |

### R-11 领域模型演进与多仓库扩展

| 维度 | 内容 |
| --- | --- |
| 风险 | MVP 单仓库绑定在数据模型上固化为 1:1，后续扩展多仓库/多团队成本高 |
| 触发条件 | MVP 后需要第二个仓库或第二个团队 |
| 影响 | 数据库重构、迁移风险 |
| 应对策略 | ① 仓库绑定表设计为 1:N，MVP 只暴露 1:1；② MUST 保存外部 ID 与原始 payload，保证可对账；③ 状态机与门禁配置化（I-8）为流程扩展留余地；④ 不提前做多团队功能（6.2 非目标） |
| 验证方式 | 数据模型评审 |
| 升级条件 | 新增仓库需求出现 → 由产品负责人决策扩展方案 |

### R-12 数据备份与恢复

| 维度 | 内容 |
| --- | --- |
| 风险 | 生产数据丢失导致追踪链与度量不可恢复 |
| 触发条件 | 数据库故障、误删 |
| 影响 | 交付证据丢失 |
| 应对策略 | ① 数据库定期备份；② MVP 验收前至少执行一次恢复演练；③ 删除操作软删除优先，物理删除需授权 |
| 验证方式 | 恢复演练 |
| 升级条件 | 备份不可用 → 立即升级 |

## 14. 决策方法（不确定时怎么办）

实施与使用过程中遇到本 PRD 未覆盖的情况，按以下顺序判断：

1. 查本 PRD 权威章节（0.1 权威关系）。
2. 查实施计划、留痕记录与历史决策。
3. 验证当前代码与运行状态——历史文档只能作为线索，不能直接当现实。
4. 仍不清楚时，按优先级选择：保持契约稳定 > 保留原始事实 > 符合当前优先级 > 实现最轻量。
5. 涉及契约、权限或不可逆操作时，停止并请求确认（5.4）。

## 15. 任务边界与完成标准

### 15.1 任务边界

1. 每一行修改都必须能追溯到当前需求。
2. 不顺手修改无关代码、注释或格式。
3. 新建抽象前，先确认它是否服务于多个真实场景。
4. 发现主线外问题时，只记录，不在当前任务中扩展。

### 15.2 完成标准

- [ ] 修改范围与任务一致
- [ ] 必要测试通过（单元、集成、对账相关）
- [ ] 契约与文档已同步
- [ ] 未引入凭证或本地环境文件
- [ ] 已说明未验证部分与剩余风险

## 16. MVP 验收标准

MVP 达成标准：

1. 用户可以创建需求、完成评审、进入计划、拆分任务，并在验收后关闭需求。
2. 用户可以连接一个 GitHub 仓库。
3. 用户可以从任务创建 GitHub 分支，分支名符合规范。
4. 平台可以同步提交、PR、评审和 GitHub Actions 状态。
5. 平台可以在任务和需求上展示 PR 与 CI 门禁状态及失败原因。
6. 测试人员可以创建测试用例、记录测试结果，并创建阻塞缺陷。
7. 发布负责人可以创建发布单、纳入需求、检查门禁、触发或记录部署、完成生产验证并关闭发布。
8. 需求详情页可以展示端到端追踪链路。
9. 度量页面可以展示团队流动、PR、构建、测试和发布指标。
10. 门禁失败时，平台能说明失败原因和需要修复的内容。
11. （新增，R-1/R-4）重复、乱序或丢失的 Webhook 事件不会导致数据重复或状态错误；对账可以恢复缺失事件。
12. （新增，R-3）无法自动匹配的对象出现在未关联队列，并可人工关联。
13. （新增，R-5）仓库绑定向导能提示 Branch Protection 缺失项。
14. （新增，R-6）部署状态缺失或超时时，发布单显示异常并可人工处理。
15. （新增，R-7）状态流转全部有时间戳；指标样本不足时明确显示。

## 17. 建议实施切片

### 切片 0：工程基础与留痕机制

工程骨架、留痕模板（Source / Plan Task / Requirement / Review / Tests / Acceptance / Retro）、基础 CI。支撑第 15 章任务边界与完成标准。

### 切片 1：需求与任务闭环

需求中心、评审中心、迭代与任务中心、状态机（含时间戳留痕）、需求进入开发门禁（10.1）。

### 切片 2：GitHub 连接

仓库绑定（含 Branch Protection 检查清单）、从任务创建分支、Webhook 接收（签名校验、幂等、原始事件存储）、提交与 PR 同步、未关联队列（11.4）、对账机制基础（11.3）。

### 切片 3：CI 与门禁可视化

workflow run / check run 同步、PR 合并门禁展示（10.2）、流水线中心。

### 切片 4：测试与缺陷闭环

测试用例、测试计划、测试结果、缺陷与阻塞规则、发布门禁输入。

### 切片 5：发布与部署闭环

发布单、发布门禁（10.3）、workflow_dispatch 触发、部署多源状态汇总（5.3）、超时与人工处理、回滚记录。

### 切片 6：验收与度量

生产验证、业务验收、复盘项、需求关闭门禁（10.4）、度量看板（含数据完整性检查）。

切片顺序理由：

1. 先有工程与留痕机制，再开始功能开发。
2. 先有领域模型、状态机与门禁，再接入 GitHub。
3. 先有代码链路与对账，再依赖 CI 数据。
4. 先有测试与发布闭环，再做验收与度量。

## 19. 实施计划默认决策

后续实施计划按以下默认决策展开：

1. 产品形态：可部署 Web 应用。
2. 团队范围：MVP 阶段一个团队、一个项目、一个 GitHub 仓库。
3. GitHub 集成方式：GitHub App（最小权限）。
4. 部署触发：配置后通过 GitHub Actions workflow_dispatch 触发。
5. 部署状态来源：deployment_status 事件优先，其次 workflow run 状态，最后人工确认（标记来源）。
6. CI 引擎：MVP 仅支持 GitHub Actions。
7. 合并硬约束：GitHub Branch Protection 是实际阻断层；平台负责计算和展示交付门禁（R-5）。
8. 前后端技术栈：实施计划阶段结合现有工程约束选择。
9. 数据库：实施计划阶段选择，优先关系型模型（I-8、R-11）。
10. 仓库绑定模型：数据层支持 1:N，MVP 仅暴露 1:1（R-11）。
